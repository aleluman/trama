1. Goal and status

Trama lets any React application define typed business forms and run their rules without mounting a UI. An application provides the business logic, renderers, and data access. Trama maintains the state of each edit and coordinates changes between fields.

The package includes independent sessions, derived values and state, events, bidirectional relations, remote selections and queries, row collections, rule sets, per-field presentation, validation, and submission preparation and commit. The ESM entry points with TypeScript declarations are trama-forms/core and trama-forms/react. The production target is modern browsers. The README contains the working instructions. The interactive guide is published on GitHub Pages and documents the latest release.

2. Responsibilities and structure

  • Core. The session owns values, the baseline, field state, row identity, outputs, and queries. src/core/index.ts exports the interface. compile.ts, forms.ts, and the authoring modules compile definitions. session.ts, engine.ts, operation.ts, and resolution.ts coordinate writes, evaluation, and publication. The row, state, list, query, and submission modules maintain their invariants within the session or, for lists, within each view.
  • React binding. src/react/index.ts exports the renderer registry, hooks, and adapters. opening.ts coordinates opening, field.ts and render.ts connect fields, and async.ts, rows.ts, outputs.ts, and form-state.ts adapt the public subscriptions. The binding imports the core's public entry point.
  • Application and services. The application defines fields, rules, endpoints, and renderers, transforms the prepared submission into its payload, and decides when to commit it. The services handle authorization, final validation, and persistence.

3. Needs it meets

  • Open existing records or start with defaults, edit several records at once, and represent the same session in two views.
  • Calculate amounts and summaries, populate or clear fields when a selection changes, and keep two editable representations of a piece of data consistent.
  • Adapt labels, limits, visibility, required status, and read-only status to the values and opening context.
  • Search paginated options, hydrate saved selections, and apply remote responses without overwriting later edits.
  • Edit and reorder line items with stable identity, reuse rules across definitions, and prepare a submission with its errors at their locations in the view.

4. Execution contracts and invariants

  • An operation prepares a candidate and publishes a consistent view. During resolution, reads see the candidate's resolved values. The affected state, outputs, and parameters are then evaluated. Subscribers read the published snapshot. An incompatible write, a failed synchronous rule, or a cycle rejects the candidate. Failed outputs and observer failures have their own channel.
  • The session validates writes even from JavaScript. An undefined in a patch skips the write. Falsy business values are preserved when their type allows them. An edit with the same value publishes and notifies subscribers of a new snapshot with equal content, without reevaluating formulas or events. Reentrant operations that write during an operation or notification are rejected.
  • A definition is reused in independent sessions. Snapshots are read-only and preserve records and arrays that do not change. Row order is published along with the row keys. Declaration order determines precedence among writers that participate in value resolution.
  • A remote response writes only when its generation and the revisions of all its targets are still current. Aborting saves work when the transport permits it. Acceptance is still checked if the transport responds after being aborted.
  • Validity, interaction marks, and "dirty" are independent. The prepared submission captures a point in the edit. Committing updates the baseline and preserves later changes.

6. Current architecture decisions

  • Independent core with one session as the sole owner of state. ADR 0001
  • Property-based rules and field events. ADR 0002
  • Typed endpoint registry and loader-controlled cache. ADR 0003
  • Independent lists per view and queries by generation in the session. ADR 0004
  • Stable row identity, per-row values, and targeted invalidation. ADR 0005
  • Variants through composition of rule sets with explicit requirements. ADR 0006
  • Base value types, dynamic state, and static subtype presentation. ADR 0007
  • Model validation, baseline comparison, and two-step submission. ADR 0008
  • Direct edits, ordinary mode fields, and relations declared on their driver. ADR 0009

8. Dependencies and reuse

The core has no production dependencies. React 19.3 is an optional peer dependency of the binding. The integration with TanStack Query v5 is structural. initialFromQuery accepts the result of an application hook, and queryLoader accepts a client with fetchQuery. The application installs and configures its client when it uses that integration. The guide and tests include React, React DOM, and TanStack Query as development dependencies.

pnpm and its lockfile pin the tools. The package is installed with npm install trama-forms. GitHub Actions runs pnpm run check on every pull request and on main. From 0.1.1, each v* tag in aleluman/trama runs the gate, packs the package, and stages that tarball on npm through trusted publishing, with provenance. A maintainer approves each staged version on npmjs.com with two-factor authentication before it becomes public. Version 0.1.0 is published by hand, because trusted publishing can only be configured for a package that already exists. TypeScript checks types and emits the core and declarations, Oxc compiles the React binding's JavaScript, and Vite builds the guide. Oxlint with type analysis and Oxfmt check the source code. A new dependency requires a concrete need and must respect state ownership and the independence of the core.

9. Capabilities

Define, open, and edit forms

createSession(definition, { initial?, scope?, loader?, context? }) accepts a definition created by defineForm. Two openings of a definition always have independent state. The core applies, in order, each type's empty value, the field's default, defaults(context), the fields supplied in initial, and the value formulas of omitted fields. The formulas of supplied fields record their reads. It then stabilizes state and outputs and captures the baseline. Events are reserved for the operations that trigger them. A partial initial preserves 0, false, "", and null where allowed. An explicitly undefined field in initial is an incompatible value.

edit(name, value) validates and publishes synchronously. getSnapshot() returns the current view, and subscribe(listener) returns the unsubscribe function. reset() restores the baseline values and rows and recalculates state and outputs. It resets the relevant value queries to idle and aborts the signals of any requests that were in flight (queries). A reset that fails during restoration leaves the queries untouched. Restoration excludes value formulas and events and leaves the source that loaded initial intact. Value query responses applied after opening or resetting can make the form dirty because they arrive after the baseline is established. Copied definitions are rejected with Form definition must be created with defineForm, an opening input other than a values object with Initial values must be an object, and a reentrant write from a notification with, for example, Cannot edit a session during its notification.

createReactBinding validates the registry and its options. When opening, useFormSession checks coverage of the entire definition, including hidden and row fields. When connecting, Field checks its session's definition or the row handle's template. useFormSession(definition, { key?, initial?, scope?, context? }) returns FormEditor<D>, with branches loading, error with error and retry(), and ready with session. A different key opens another session within the same hook. The key accepts a string, a finite number, or undefined. The same key fixes the definition and scope and, from ready onward, fixes the context by structural equality. Changes are reported as Changing definition requires a different session key, Changing scope requires a different session key, or Changing context requires a different session key. A ready session ignores new references to initial and query updates.

initialFromQuery(query) wraps an application InitialQuery<T> with data, error, status, isEnabled, isStale, isPlaceholderData, dataUpdatedAt, and refetch. The source type is fixed when the opening is created. Switching from a query to values during loading is ignored, and the in-flight response can still open the session. While the opening is loading or displaying an error, it uses the context from the last update committed by React. A disabled query waits. Before ready, real, fresh data from a successful query is accepted, or a refresh is requested in an effect with { cancelRefetch: false, throwOnError: true }. That refresh requires success, data that is present and is not placeholder data, and a strictly later dataUpdatedAt. Its result can become stale immediately, for example with staleTime: 0. An identical or earlier timestamp produces Initial query refresh could not be verified (cancelled or coincident timestamp); retry if the source has no error of its own. A success with no data produces Initial query has no data. retry() forces another refresh if the opening is still active in that error state. Changing the key, unmounting the editor, disabling the query, or hiding the editor with Activity invalidates the local opening attempt. When the query is enabled again or the editor is shown, a normal opening can accept fresh cache data, and a retry still requires a refresh. The shared initial query remains under the control of the application and TanStack Query. Synchronous opening failures throw, and failures accepting data from a query reach error.

Once the session is ready, unmounting or changing the key removes the view's subscriptions. Value queries and a pending preparation from the previous session can finish in that session. Their results stay in that session, and the new one rejects its prepared submission. The application can pass its own signal to prepare and abort it when leaving the view. In StrictMode, each candidate session can start requests with the direct loader. queryLoader can deduplicate them.

Field receives session or row, name, and, depending on the type, overrides for label and placeholder. Two views share value and state and have distinct IDs. Each field observes its value, its state, and resetVersion. Changing sessions or resetting remounts the renderer. The committed numeric value is number | null. The renderer retains transient text, converts and formats it, and reflects value changes that come from another view. The build emits ESM and declarations for both entry points and applies Oxc's React compiler to the binding's JavaScript.

Evidence. core, operations, React, rendering, real TanStack Query, scripted source, opening context, coverage when connecting, queries in React sessions, and installed package. In the guide, see Sessions, React, and Loading with TanStack Query. The contact example opens a session with Ana, edits the age to 34, and returns to the baseline.

Outputs, state, and observers

outputs: ({ output }) => ({ … }) publishes a map of references that belong to the definition. Each output((values, { read, context }) => result) infers its result and can read other references from the same definition, including intermediate references without published names. Outputs read the operation's stabilized values. Their formulas are synchronous, their dependencies come from reads, and their results feed views and other uses in the application. Field rules read form values.

Results are validated, copied, and frozen. They also allow undefined, bigint, symbols, and non-finite numbers as output data. Functions, accessors, class instances, and cycles are rejected. Equality applies Object.is to primitives and recursively compares the data's own properties, including symbol keys and array holes. An equal result preserves the public reference. An initial failure or a cycle between outputs still allows the session to open. Failed outputs and their dependents remain unavailable until reevaluation recovers them. A read throws Output "x": calculation failed: … with its cause. Reads made before the failure are retained, and an independent output remains operational. Resetting reevaluates the outputs.

session.watchOutputs(callback, { onError }?) runs immediately and when outputs read during the synchronous callback change. Each run replaces that selection and includes the names it attempted to read even if the callback fails. Recovery notifies again even if it recovers the last valid value. Unsubscribing is idempotent. The callback can capture values for its asynchronous work. Synchronous failures go to onError and, if it is absent or fails, to reportError or a deferred throw. subscribe notifies subscribers of the snapshot, including the updated fieldStates, and reports failures through the same global mechanism. Neither rolls back publication or prevents the other notifications.

useOutputs(session) tracks names read during the committed render, even if branches change. Spread and rest extend the set of names read. A nested read selects the whole output. OutputBoundary takes session, children, and fallback. It recognizes a failed read of an output from its session and replaces its children. It remounts the children when the output recovers, including when the children failed before subscribing or when the output recovers its last valid result. While the fallback is showing, a change to an output unrelated to the failed read leaves the fallback mounted. Placing the editor outside the boundary preserves its tree. Other errors follow React's handling.

Evidence. domain and equality, failures and observers, chained outputs, React selection, and boundary recovery. In the guide, see Derived outputs. The amounts demo calculates the subtotal, discount, 20% tax, and total in JPY.

Authoring by field property

rules is a map whose entries name fields or collections. value accepts a synchronous formula. (values, { peek, context }) reads the operation's final values and tracks reads of values, including during destructuring. peek participates in resolution and value cycle detection without recording triggers. Reading a value formula's own field with values or peek is a cycle. Reads after the return do not record dependencies. The value formula is evaluated on opening and then when a tracked read changes. undefined preserves the value, and a direct edit of a calculated value persists until a dependency changes, subject to the additional relation rules.

onChange: (values, tools) => patch | undefined triggers if its field ends up with a different value from the previous one, including due to a rule or response. The event can read other resolved fields. Those reads do not trigger it. tools includes context, toDefaults(...names), before, and, in the header, rows. toDefaults returns a patch with the session defaults calculated on opening, including the type's empty value where applicable. No event runs as a result of opening or resetting. An empty or omitted patch performs no writes, and a target with undefined is ignored. onChange writes can take precedence over values the command supplied in other fields.

The engine resolves each target in declaration order, including rule sets and their inclusions. The last active writer with a defined result takes precedence. A writer that returns the current value participates in that precedence. When an event reveals an already resolved target, the session returns to the relevant point and discards that attempt's affected work. Each applied result uses the candidate's consistent values. Authoring functions are pure and synchronous and can run again during resolution. Values and read tools are read-only.

Circular value dependencies and event writes back to the event's own field or to data it depends on are rejected even if the values converge. The diagnostic identifies the name, property, and path, for example Field "a" value: cyclic dependency a → b → a. A formula error preserves its cause, as in Field "total" value: formula failed: …. If a formula or event catches a read failure, the operation is rejected with the original diagnostic for the target that was read. Results such as Infinity for a number or a promise in an event are rejected. An event that returns null produces Field "country" onChange: expected a patch object, got null. Field keys that JavaScript orders as indices produce, for example, Field "0": names that JavaScript orders as indices are not allowed.

Validation of the map and its entries distinguishes Form rules must be an object keyed by field, Rules: unknown field "totl", Field "total" rules: expected an object of properties, and Field "total" rules: unknown property "valeu". Properties without a function produce, for example, Field "total" value: formula must be a function or Field "country" onChange: event must be a function. Invalid patch targets and values retain the event prefix, as in Field "quantity" onChange: unknown field "citi" in patch and Field "quantity" onChange: incompatible value null for text field "city".

Evidence. reads and peek, formula errors, order and cascades, event and patch diagnostics, target resolution, and undefined. In the guide, see Value formulas and Events. The country and city example selects among Spain, Mexico, and Japan and uses Madrid, Mexico City, or Tokyo when asked to populate the capital.

Extended state and form lock

State starts from the field declaration and receives contributions from property formulas, states, and, for readOnly, the lock. The formulas read final values, including their own field. They are evaluated on opening, on reset, and when their tracked reads change. A failure rejects the operation and preserves the previous contributions. disabled and readOnly accept one formula or an array of formulas. Each formula can return a boolean, a nonempty reason, or undefined. hidden accepts a boolean, and required also accepts a nonempty message. Any active contribution sets its flag. false or undefined removes only its own contribution. An empty array is equivalent to omitting it, and holes or elements other than functions are rejected. Value or event failures are reported first, followed by failures in state, parameters, and locks in declaration order.

label and placeholder accept a formula with string | undefined. The last defined contribution wins, including "". placeholder requires a type whose definition allows it. reasons combines the reasons for disabled and readOnly, deduplicated by first appearance. The order starts with the field, continues through the rules with their arrays and patches in declaration order, and ends with the lock. states contributes properties to several targets and replaces its entire contribution on each evaluation. The targets of a header rule are header fields. The targets of a row rule belong to its own row. A target or property that disappears removes the contribution. value is rejected in a state patch.

form.readOnly accepts a { value, except? } entry or an array of entries. Each value is a formula that contributes read-only state to header and row fields. except is a static array of header names or objects naming fields in a collection, for example ["notes", { lines: ["notes"] }]. Each exception removes only that contribution. An invalid target produces, for example, Form readOnly[0]: unknown field "x" in except. A patch with an incompatible property produces Field "delivery" states: unknown property "value" for field "city". Evaluation failures identify the field, property, and index if applicable.

The core maintains the identity of the state and its lists as long as their content is equal. The flags preserve the value and allow core writes. Field still observes the field if hidden removes its renderer from the tree. Its onChange checks the current state and ignores changes while the field is disabled or read-only, even with a previously captured handler. View props take precedence over the state's label or placeholder. Required status is checked in validation.

Evidence. combination, patches, diagnostics, row exceptions, and rendering and editing. In the guide, see Field state. The labels example shows "Municipality" and "E.g., Madrid" when Spain is selected.

Endpoints, remote select, context, and value queries

Registry and hydrated options

defineEndpoints({ key: endpoint.…(load) }) declares a Registry. endpoint.options receives ({ search, page, signal, scope }, params) and returns Promise<{ options, more }>, with pages starting at 1. endpoint.list receives ({ signal, scope }, params) and returns all options. endpoint.value uses the same request and returns a plain data value, including undefined. createForms({ endpoints: [registry, …] }) combines keys and rejects duplicates with Endpoint "customers" is declared in two registries. field.async(key, config?) and field.multiAsync(key, config?) from the bound registry accept options or list keys. A value endpoint receives the diagnostic Endpoint "x" gives a value; use an options or list endpoint. Forms and rule sets with remote fields or queries are declared with the bound functions.

Option has a value of type string or finite number and a label of type string. It can carry plain-data metadata. Selections store complete options, deeply copied and frozen. Opening values that are already hydrated let the selection be displayed before lists load. An option with the same value preserves that field's current option, including its metadata, without triggering changes. A remote value must include the complete option. Incompatible data in the metadata is reported with its path, for example Field "customer" (async): option must be plain data: a Date at "since".

Context, parameters, and loader

declareContext<T>() declares a plain object for opening, distinct from the remote scope. The session requires context when it is declared, with Form requires a context, and rejects a defined context when the declaration is missing, with Form declares no context. The session validates, copies, and freezes the data before calculating defaults(context) once. At runtime it checks that the data is plain and checks the default values. The keys of type T are checked in TypeScript. Context stays fixed during the edit, and rules, outputs, and query patches read it. A default failure includes Form defaults: formula failed: … and its cause.

A form with remote fields or queries requires a scope, a string or finite number, and can optionally receive a Loader. If the scope is missing, the session reports Form with async fields requires a scope or Form with queries requires a scope. The LoadKey is ["trama", scope, endpoint, params], followed by the search and page for a paginated endpoint. Loader receives (key, run, { signal }), where run(signal) calls the endpoint and validates and freezes the result before it reaches the cache. The direct loader has no cache. queryLoader(client) uses fetchQuery, the TanStack Query signal, and its shared cache, with structuralSharing: false. Freshness follows the application's policy. If one caller stops waiting for a shared request, its local abort leaves the TanStack Query request running. Invalidating that cache alone does not refresh a Trama list.

params on a remote field or query.params is evaluated as a tracked state formula. It returns a plain object or undefined to suspend. Without a formula, {} is used. The object is copied in canonical form, object properties with undefined are omitted, and data is compared independently of identity. undefined inside arrays and the keys __proto__ and constructor are rejected. An invalid result produces, for example, Field "contact" params: incompatible result 5, expected a plain object or undefined. TypeScript requires the formula if the endpoint has required parameters. In JavaScript, omitting the formula still sends {}. Suspending a list or query preserves the previous selection or value. The application declares any automatic clearing or selection.

Lists per view

session.list(name) and row.list(name) create an OptionList<O> per call. Its stable OptionListSnapshot<O> contains { status, text, options, complete, error }, with statuses idle, suspended, loading, ready, and error. Actions change the view. The first subscriber synchronizes parameters and enables requests. The subscribed list checks its parameters on each publication by the session engine. When the last subscriber leaves, an in-flight request is invalidated and aborted, and the list stays in loading. On resubscribing, the parameters are resynchronized and loading resumes if applicable. Lists do not write to the session.

open() restarts from the first page with the current text. search(text) opens the list and updates the search. In JavaScript, non-string text throws Field "customer" list: search text must be a string. With endpoint.options, it requests from the first page. With endpoint.list, it filters labels locally, ignoring case and accents, when the complete list is available. more() requests the next page when the list is ready and incomplete. retry() retries the current page after an error. Previous pages are retained when advancing or if the next page fails. Duplicate values within a page or a complete list are rejected. Across pages, the first occurrence takes precedence. An empty list can be ready, and an empty page with more: true remains incomplete.

An effective change in parameters invalidates the request, discards its pages, and preserves the text. An open list requests again when enabled. A stale response never replaces the current list. Field "customer" list: request failed: … remains in the snapshot with the original cause, including malformed responses such as Endpoint "customers" page 1: expected { options, more }. Requesting a list for a non-remote type throws Field "note" (text) has no option list. The renderer chooses how to delay the search and display the error.

When a row is removed, its subscribed list suspends and aborts the request. If reset restores the row, the list returns to idle or requests again if it was already open. Moving the row preserves its text and attempt. If reset leaves the same parameters, a core list can keep its request. In React, each visible renderer of a remote Field creates and subscribes to its own list even if no one opens it. The list is removed with the renderer when the field is hidden. A change in resetVersion remounts the visible renderer with a new list.

Queries that write values

query: { endpoint, params?, patch?, forPrepare? } goes in the entry of a field of any type and uses a value or complete-list endpoint. Each entry accepts one query. The entry's field identifies the query. On opening, it requests if it has defined parameters and the field was omitted from initial. An accepted explicit value, including null, counts as supplied. A default does not count. Reset invalidates the previous generations and starts new requests according to the baseline and its supplied fields. After a commit, it uses the committed baseline. A subsequent parameter change requests again. An edit that changes the entry field invalidates its generation, even if the parameters stay the same. session.retry(name) restarts the request with the current parameters, if any. A name without a query throws Field "x" has no query. Changing to undefined parameters invalidates the request without replacing it and leaves the query in idle.

Queries require the defineForm or defineRules from createForms. With the standard functions, at runtime an entry with query first produces Field "price" query: define the form with the defineForm of createForms or, in a rule set, Field "price" query: define the rule set with the defineRules of createForms. The type error uses the defineForm text in both cases. With the registry-bound functions, the definition checks, in order, the shape of query, its properties, the registered endpoint and its kind, the params and patch functions, and the forPrepare boolean. Diagnostics include the entry prefix, as in Field "price" query: expected an object with endpoint, params, patch and optional forPrepare, Field "price" query: endpoint "customers" is paged; use a value or list endpoint, and Field "price" query: forPrepare must be a boolean.

Each current response evaluates patch(result, { values, context }) against the published values without tracking them. With patch absent, it attempts to write the result to the entry field. undefined skips the write. A header query can write to header fields. The patch callback runs outside the publication guard. If it starts another operation, the generation is checked again. The loader, the endpoint, and abort callbacks that run during publication are under the guard, and their reentrant writes are rejected. If any target's revision has changed since the request, even if the target returned to its previous value, the entire patch is discarded. Only accepted writes participate in onChange events, formulas, and state evaluation. The row capability details the shared response batch.

snapshot.queries publishes QueryState per header entry, with status: "idle" | "pending" | "error" and error. A change only to query state preserves values, fieldStates, and resetVersion. If only a row query's state changes, the handle publishes the change. Session subscribers are notified, and getSnapshot() can return the same object. An error preserves values and stays local to the query, for example Field "price" query: request failed: …, Field "price" query: patch failed: …, or Field "price" query: response operation failed: …. The cause of wrapped failures is preserved. An invalid patch is identified by its shape, target, or value. Queries marked forPrepare are considered when preparing a submission.

Rows, targeted invalidation, and rule sets

Identity, operations, and reads

collections: { lines: { fields: { … } } } declares collections separate from the header. initial.lines accepts partial rows, with defaults for omitted values. An omitted collection opens empty. RowKey<N> is an opaque key branded by collection, unique within the page's global scope and never reused. Editing and moving preserve the key. The field representing a persisted identifier, when present, is ordinary data. values.lines, fieldStates.lines, and rows.lines correspond by visual order. The key array preserves its identity until membership or order changes.

session.row(collection, key) returns a stable RowHandleOf<D, N>. add(collection, rows, { at }?) adds at the end or between 0 and n and returns the keys in input order. It evaluates the new row's formulas and honors its supplied values without running that row's events on creation. remove(collection, keys) removes each key once, and move(collection, key, to) uses the final position, between 0 and n−1. patch({ field, lines: { [key]: { field } } }) writes to the header and rows in one operation. A command validates the entire batch before resolving it. A rejection does not publish, change rows, or start requests. If nothing changes, it publishes a new snapshot and notifies subscribers without reevaluating rules. values, rows, and fieldStates, including the collection's key array, preserve their identity. The session's edit applies to the header.

The handle offers getSnapshot, subscribe, and edit, as well as remote operations and interaction marks. When the row is removed, getSnapshot() returns undefined, and writing or using its individual operations throws Collection "lines": row "r3" was removed. If reset restores the row from the baseline, it revives its key and handle. A foreign key is rejected with Collection "lines": unknown row key "r9", and an invalid position with, for example, Collection "lines" move: position 2 is out of range 0..1. A rule diagnostic includes the row key, as in Field "amount" of "lines" row "r3" value: formula failed: …. React connects Field row and useRows(session, collection). useRows tracks membership and order.

In rules.lines.each, each formula receives (row, { values, key, peek: { row, values }, context }). An event receives the row and tools with values, key, toDefaults, before, and context, and writes to its own row. A header event gets the keys through rows and can target specific rows in its patch by collection and key. Reading collection values creates a dependency on membership and order and adds a dependency for each row field read. Reading only a key to target a patch avoids reading that value. Reordering reevaluates whatever reads the structure. Creation order is stable for rule traversal, except for the order in which a dependent rule traverses the data it reads.

Invalidation reaches the fields and rules that depend on the change, with structural sharing per row. An aggregate that reads a column depends on the fields it traversed. A formula repeated in each row that reads all the other rows can reach the entire collection. That case falls outside the budget for a targeted edit.

Lists, queries, and batching

Each remote row field computes its own params, and row.list(name) creates a list for that view. row.getSnapshot().queries and row.retry(name) are limited to the row. Queries start in the header and then by collection, row creation order, and declaration order. After an edit, each header query decides in turn whether to stop and whether to request again. In rows, queries whose field changed are stopped first, and then new requests start in the same order as on opening. New rows also query when their entry fields were not supplied. Moving a row preserves its query. Removing it or resetting invalidates its generations. patch(result, { row, values, key, context }) writes only to its own row. A header query that tries to write to a collection receives Field "price" query: patches cannot write collection "lines".

The flush in the microtask that the first response schedules gathers the outcomes that arrived before the flush, from the header and rows. Patch callbacks read the published state on arrival. At the flush, generations and target revisions are checked again in arrival order. The first response to write to a target reserves it, even when it writes the current value. A later response that shares that target is discarded in full. In the first grouped pass, all responses are compared against the state before the batch. Discarding a response due to revision or overlap leaves the query in idle if the generation is still current. If the batch changes a query's parameters, its accepted response can write, and the query requests again with the new parameters. The union of accepted patches is applied as one operation, with a notification that includes all current outcomes. If that operation fails, each response is processed separately in arrival order. The patch calculated on arrival and the before from the start of the batch are retained, but each response rechecks its generation and revisions against the state left by the earlier responses. This reconsiders an overlap, discards an outcome that became stale, and preserves any new generation.

Rule set composition

defineRules({ fields?, collections?, context?, rules }) produces a RuleSet by identity that declares its requirements. include fixes variants when the definition is compiled. false, null, undefined, and holes are skipped. The system checks identity and duplicates, membership in createForms for bound rule sets, and requirements for fields, collections, types, endpoints, and context. TypeScript also compares value and context types. Effective labels, defaults, and catalogs belong to the definition. Rule sets contain rules and requirements, so sharing a lock or an output is part of the application's own composition.

The declaration sequence starts with the rule sets in include order, followed by the form's inline rules. State contributions accumulate in that sequence. value, each event, params, and query allow only one declaration per field, with mutual exclusion between onChange and onEdit. Relations also claim their generated properties. A duplicate reports both locations, for example Field "amount" of "lines" value: declared by include[1] and include[2]. A rule set bound to another createForms instance produces Form include[0]: rule set of another createForms. Required parameters must be covered in every accepted alternative. A rule set has no include of its own, and variants that use it must declare all its requirements.

Date, multi-select values, decimals, limits, and subtypes

field.date represents a Gregorian civil date, from 0001-01-01 to 9999-12-31, or null. It checks the strict format and calendar, including leap years. An invalid write produces Field "since" (date): expected a civil date YYYY-MM-DD between 0001 and 9999. DateFieldProps keeps that value and its limits as text. The library has no date type with a time component.

field.multiSelect accepts an array of value entries from its catalog, and field.multiAsync accepts complete remote options. The empty value for both is []. Each write first validates the entire array, including holes, accessors, membership, and duplicates. The messages give the reason, as in Field "kinds" (multiSelect): duplicate value "sale". The same members in a different order preserve the previous array and do not trigger changes. When the members change, a frozen copy is stored in the written order. multiAsync reuses the field's current options by value, and a renderer retains selected options that do not appear on the visible page. A complete-list endpoint can write the entire selection with query without a patch. MultiSelectFieldProps and MultiAsyncFieldProps preserve the type of that array.

Numbers accept decimals, min, and max. Dates accept min and max. These are declared on the field, in property formulas, or in states. decimals is a nonnegative integer. Limits are finite numbers or civil dates of the corresponding type. The last defined contribution wins. In rules, undefined removes the contribution, and null in min or max removes the preceding limit. The state and props provide the resulting limit or undefined. null in the definition or in decimals is rejected. min ≤ max is checked in the definition and in the final combined state. If the combined state has min > max at runtime, the operation is rejected, for example Field "price" of "lines" row "r3" (number): min 10 exceeds max 5. Decimals and limits preserve the value. Validation checks the inclusive limits, and the renderer applies its formatting.

createForms({ endpoints, subtypes: { name: subtype.text<P>() } }) adds the field.name factory based on its base type. presentation is a copied and frozen plain object typed according to P. The subtype preserves the base type's values, rules, lists, and properties. Remote subtypes receive their endpoint key, and OptionKey can link presentation keys to that endpoint's option. createReactBinding(renderers, { forms }) requires the subtype entry under its own name. The renderer receives the base type's props and presentation, which it can type with SubtypeProps<typeof forms, "name">. Reusing the base renderer requires registering it for the subtype as well.

Acceptance in forms, rule sets, and bindings is checked by identity at runtime. A field from another forms can match structurally in TypeScript and be rejected at runtime. JSON serialization loses the identity. Using a base name as a subtype is rejected, for example Subtype "date" has the name of a field type. Without a specific renderer, Field "notes" (subtype "textarea"): missing renderer appears. At runtime, presentation is validated as plain data. Its specific keys are checked by the type system. When combining subtype modules with object spread, a repeated key silently retains the last declaration that reaches createForms.

Validation, changes, and submission

Validation and baseline

error and warning receive a formula or an array of state formulas. Each result is a nonempty message, false, or undefined. They are declared per field, in states, in rules.<collection>.row or .collection, and in form. row evaluates per row, and collection per collection. Each target's messages preserve declaration order without repeating text. The counts for a scope tally targets with messages, including its descendants. A scope's state retains its own message text.

required validates against the type's empty value, including false in a checkbox. Its text comes from the last active contribution that includes a message. min and max validate a nonempty value. Validation failures precede rule errors. Hidden, disabled, or read-only fields remain in the model and are validated. createForms({ endpoints, messages }) accepts optional required and query functions with { label }, and min or max with { type, min | max, label }. The registry fixes these functions at creation. Changing the configured language requires another registry and another session. The default texts are Required, Minimum <limit>, Maximum <limit>, and Could not obtain required data. Invalid text rejects the operation with a diagnostic such as Validation message min: expected a non-empty string, got "". Patterns and other business rules are expressed with local messages.

dirty compares against the baseline using the type's equality. It uses value for remote fields and set equality for multi-select values. A new row or a row with a different cell is dirty. Membership and order can make the collection dirty, and moving a row by itself preserves the row's "dirty" state. A change in the header or in a collection makes the form dirty. Returning to the accepted or committed initial value clears that difference. Opening and resetting publish the clean baseline.

Prepare and commit

prepare({ signal }?) checks whether the session is notifying and validates its options before canceling the previous pending attempt and marking the attempt on the form and existing rows. If the signal is already aborted, it leaves the mark and resolves to { status: "cancelled" } without waiting for queries. A row created afterward requires its own attempt. It waits for forPrepare: true queries and their batches, including required queries that start as a result of their responses. It captures synchronously when no required query remains in flight. A local error, pending input, or a failed required query produces { status: "invalid", issues }. The failed query uses messages.query with its field's label. If that function throws, the promise rejects with Validation message query: formula failed: … and the original cause. If it returns invalid text, the diagnostic requires a nonempty string. Issues appear in visual order, first the form, then the header, and then collections and rows, with a target's own error before those of its children.

A valid preparation returns a Prepared<D>, { status: "ready", values, rows, warnings }, frozen and bound to the session. It captures local and external warnings and the keys in visual order. A new attempt, a command that changes values or rows, a successful reset, or the signal causes it to resolve to { status: "cancelled" } if the attempt is still pending. If reset fails during restoration, the attempt stays pending and the queries and marks are preserved. Canceling preparation by itself lets the queries continue. A response, a touch, an operation with no changes to values or rows, or a commit does not cancel by itself. Invalid options throw, for example prepare: signal must be an AbortSignal. The prepared submission covers the entire form. While it remains live, it retains the state and engine memory from that point. The interface has no public limit on number or duration.

commit(prepared, canonical?) first checks that the prepared submission belongs to the session. One from another session or a fabricated one throws commit: prepared belongs to another session. It then validates the entire canonical patch, which covers the header and rows according to the captured keys, even for rows that have since left the live state. A key outside those captured produces, for example, commit: key "r9" of "lines" was not in prepared. Only after validation does it return false if the prepared submission predates the reset, was already accepted, or predates the last accepted one. For example, for a prepared submission from the same session that predates a reset, { note: null } still throws commit: incompatible value null for text field "note".

On acceptance, the session calculates the baseline from the prepared submission and the cascade of its canonical values. In the live pass, it applies canonical values where the target is still present and its revisions record no changes after capture. Canonical values from an earlier commit do not protect those targets against the canonical values of a later prepared submission. The live pass preserves later explicit writes that are still current and derives again when a formula replaced such a write, even with the same value. Both candidates and the new "dirty" state are validated before publishing once and returning true. An invalid canonical value or a failed cascade leaves a current prepared submission reusable.

The committed structure is the captured structure. A subsequent reset returns to the committed baseline. On that reset, a query that was still pending or had failed at preparation is requested again only if its parameters in the baseline are defined and the canonical patch omitted the entry field. A canonical value for another field can suspend the query by changing what its parameters read. Projection, transport, transaction order, and persistence belong to the application and its services.

Visibility, pending input, and external messages

session.touch(name) marks a header field. row.touch(name?) marks the row and, if specified, the cell. Editing does not mark it as touched. createReactBinding(renderers, { showErrors }) accepts "touched" by default or "attempted". In the first case, a field or row reveals its local errors when touched or when an attempt is made in its scope. With "attempted", only the attempt counts. The form and collection show their own errors after an attempt. Renderers receive visible errors, warnings, and dirty, and mark the field as touched through onBlur. useFormState(session), useFormState(session, collection), and useFormState(row) provide the scope's own state, counts, and marks. A removed row yields undefined. The result preserves its identity as long as its visible state, counts, and marks do not change.

session.input(name) and row.input(name) provide a controller per view. error(message?) reports or removes an input error, and dispose() removes it and discards the controller. Contributions from different views appear in creation order, at the start of the field's local errors. Transient text lives in the renderer. An input error sets form.inputPending and prevents preparation without changing the value or "dirty" state. Reset invalidates controllers and clears the marks. Removing a row invalidates its controllers. commit preserves those marks. Outside a notification, dispose() is idempotent. During a notification, creating the controller is allowed, and the guard rejects both error() and dispose(). Reporting from a disposed controller throws input of "since": the view was disposed. The renderer uses onInputError and clears the error after accepting the edit. Unmounting or hiding the view discards its controller.

setErrors(source, issues, { from }?) and setWarnings separately replace a source's entire contribution. The session validates the source name, options, and all issues before checking from. An invalid list throws even if the prepared submission is stale. Each issue has a message and the properties identifying its target. For a cell, TypeScript requires the key property and rejects unrelated properties even in reused objects. An unknown key produces, for example, setErrors: key of "lines" belongs to no row of this session. An empty list clears the contribution. Sources retain the order in which they were first accepted.

If the server responds with an index into lines, the application translates it with prepared.rows.lines[index]. For example, if the key identifies a row removed during saving, { collection: "lines", key, field: "price", message: "Review the price" } is skipped. An index out of range produces key: undefined. With { collection: "lines", key, message: "Review the lines" }, the message applies to the collection. Adding field: "price" in that case produces setErrors: a field of "lines" needs its row key.

With from, targets that have changed since the prepared submission are skipped, including a cell revision for its row messages and structural changes for collection messages. It returns false without replacing anything if the prepared submission predates a reset, a later commit, or the last prepared submission that wrote that source in either channel. A commit of an earlier prepared submission keeps the from of a later one current and filters the targets it changed. After committing the same prepared submission, it can be used until the next value change. A prepared submission from another session throws setErrors: prepared belongs to another session or the equivalent setWarnings diagnostic. Without from, a valid replacement returns true. A value change removes the external messages for the field or cell and for its row. Adding, removing, or moving rows removes the collection's messages. Moving preserves the row's messages. Reset removes all sources. The form's own messages are preserved until the source replaces them or a reset occurs.

External warnings and errors are always shown. The core separates externalErrors from errors, and the binding shows external errors after visible local errors without repeating messages. External errors count once per target and do not prevent preparation. warnings combines local warnings first and external warnings second without repeating text. The warning count includes each target once. The core and binding expose that combined list, and the prepared submission captures it.

Direct edits, previous values, modes, and relations

Direct edits and before

onEdit: (values, tools) => patch | undefined triggers on a change written by session.edit, row.edit, or session.patch, according to the type's equality. A repeated value does not trigger it. Rules, opening, add, reset, queries, and canonical values do not count as causes of a direct edit. Inside the handler, reading its own field gives the command's value without adding a dependency. After validating the whole patch, each patch target written by that command is discarded, even if the command repeated the value. Its other targets follow declaration precedence and can trigger formulas or onChange. A field accepts only one of onEdit and onChange, even across rule sets. A cycle that crosses the event names it as .onEdit, and an exception names it as Field "x" onEdit: event failed: ….

before is the frozen view of values at the start of the operation. In the header it is the entire form, and in a row it is { row, values }. Reads add no dependencies. New rows never appear in before. In commit, the baseline pass sees the prepared submission, and the live pass sees the prior live state. In a response batch, even during fallback, events see the start of the batch. While at least one prepared submission can still be committed, writes by onEdit count toward commit revisions or message filtering with from, even if they repeat the value. Removing an already published message requires an effective change to its target.

A mode field is an ordinary field. The guide uses a checkbox that onEdit turns on when the total changes and that the formula reads to decide when to calculate the total. Its value is part of the prepared submission, "dirty" state, and reset. Returning to automatic mode is an explicit edit of the mode field. Repeating the total's value does not activate manual mode.

Driver relations

rules.driver.relation: { default, members: { memberA: formula, memberB: formula } } declares two fields distinct from the driver and in the same scope. A text driver uses "" as its empty value. A select driver uses null and must declare exactly the two names as options. The empty value chooses the default member. The driver's final value chooses which member keeps its value, and the other member takes the result of its formula when that formula runs, unless the formula abstains. The formula for the driving member abstains without reading the other member, so application formulas can destructure the pair.

In TypeScript, checking a select driver uses the union of catalog values. A single option typed as that union can pass the static check. At runtime, the actual options are checked, including when a rule set is included. Diagnostics include Field "driver" relation: member "local" is not an option of the select and Field "driver" relation: option "none" of the select is not a member. A text driver rejects a relation with a member named "" with Field "driver" relation: a member cannot name the empty text "".

The relation compiles one value formula and one onEdit per member at the declaration site. The event sets the driver to its member. If both members change in the same command and the command omits the driver, the default member breaks the tie between the two generated events. If the command writes the driver, even with an empty or equal value, those events preserve it. Another writer to the driver follows general precedence. After a command with differences, the derived member's formula also activates if the command wrote to its field, even if it repeated the value. This recalculates the pair unless the formula abstains or a later writer takes precedence. A completely identical command preserves the pair. On opening and add, supplied members are honored.

A rule that writes to the derived member competes in declaration order with the formula if the formula activates in that operation. A query or a canonical value supplies the derived member's value, and an active formula replaces it. Activation from a write to the formula's own field is exclusive to the command. Changing a base read recalculates according to the current driver, and application calculations decide how to handle zero and rounding. Members do not accept their own value, onChange, or onEdit, and each field can be a member of only one relation. Collisions indicate the relation and where its declarations come from. An invalid final value for a text driver rejects the operation with Field "rate" value (relation of "driver"): formula failed and a cause such as the driver "driver" holds "R", which is no member. For a selection outside the catalog, the field's domain rejects the value before resolution.

11. Limits and rules for evolution

The current interface excludes these operations and forms of authoring.

  • Line-item drafts with isolated editing and independent commit.
  • Atomic replacement of an entire collection.
  • Nested collections.
  • Writes from a row to its siblings.
  • Fields added at runtime.

Definitions, relations, and variants are composed in TypeScript and fixed when the form definition is compiled. Serialization of executable rules, remote configuration of the definition, and production use in Node or through SSR are outside the contract. A capability is added when it represents a concrete need, has a verifiable interface, and keeps coordination within the module.

An effective change to params is handled immediately and can trigger a request on every keystroke. If a query's patch changes that query's parameters, the query can request again without Trama detecting the loop. retry goes through the loader again, and TanStack Query can serve it from its fresh cache. See remote field parameters, query parameters and retries, and query cache.

Option, parameter, context, and presentation types constrained by PlainRecord require an index signature compatible with plain data. An interface without that index signature can be rejected even if it declares the same fields as an accepted object alias. Conversely, TypeScript can accept symbol keys in context, parameters, and option metadata, and plain-data copying rejects them at runtime with a diagnostic that names a symbol key. See the type tests for options, endpoints, and context.
